# TreeConsole ビルド操作仕様（ドラフト）

## 1. 概要
本仕様は、TreeConsole 上でノード単位に「ビルド」操作を実行した場合の振る舞いを定義する。  
対象は `styler / shape / route` を含むビルド対象ノード、およびそれらを含むフォルダノードに対する Build の起点処理を含む。

## 2. 用語
- ビルドセッション: 1 件の実行要求に紐づくステートレスではないワークフロー単位。キュー登録され、順序どおり実行される。
- ビルドキュー: 実行待ちのビルドセッションを保持する配列。先頭到達時に実行が開始される。
- フォアグラウンドビルド: 個別ノードの「ビルド」実行時に、ビルド開始後対象ステップへ画面遷移して実行を監視するモード。
- バックグラウンドビルド: フォルダノードの「ビルド」実行時に、ビルドが自動で開始されるが、初期遷移は行わないモード。
- ステップ遷移: 対象ノードのプラグイン定義（`buildTarget`）をもとに、`build` ステップまたは代替ステップ（`data-source`）へ遷移すること。

## 3. 前提条件
1. 「ビルド」ボタン/メニューは、対象ノードが「ビルド可能」な場合のみ有効化される。
2. ビルド開始は `build` アクションの共通ハンドラを経由し、ビルドキューへ 1 件として登録される。
3. ビルドセッションは、ノード種別ごとに同一のエンドポイントではなく、対象ノード情報を含んで起動される。

## 4. ビルド可能判定
### 4.1 非フォルダノード
- 非フォルダノードは以下を満たす場合にビルド可能:
  - `buildRequired` が真
  - または、ビルドターゲットのステップ番号が解決可能
- スタイルプラグイン（`styler`）は `build` ステップが無くても `data-source` ステップにフォールバックできるためビルド可能扱いとなる。

### 4.2 フォルダノード
- フォルダノードは、配下のビルド可能ノードが存在し、少なくとも 1 件でもビルド対象ならビルド可能扱いとなる。
- ビルドキュー登録時には、対象ツリー配下を走査してビルドURLを収集する。

### 4.3 フォルダ要ビルド表示ルール
- フォルダの「要ビルド」表示は、配下ノードの判定結果を集約して算出する。  
  すなわち、配下のノードに `buildRequired=true` かつビルドターゲット解決可能なノードが 1 件以上存在する場合、上位フォルダは「要ビルド」として表示される。
- 表示判定の評価は `collectBuildUrlsFromDescendants` 相当の収集ロジックに準拠する。  
  - 収集件数 > 0 → フォルダはビルド可能
  - 収集件数 = 0 → フォルダはビルド不可（表示不要）
- 直下のフォルダノードは収集対象から除外される。

## 5. ビルド開始の共通仕様
1. ユーザーがビルドアクションを実行すると、ビルドセッションは即時にキュー末尾へ登録する。
2. キューの先頭になった時点で自動開始される。
3. 実行中は UI に進行状態（進捗/ボタン状態）を反映する。
4. 「停止」により進行は取り消しまたは一時中断される仕様は既存セッション制御に準拠する。

## 6. 個別ノード（styler/shape/route）のビルドフロー
1. ビルドアクション発火時、対象ノードの `buildTarget` を解決する。
2. 解決順は次とする:
   - `build` ステップが存在する場合: そのステップへ遷移
   - それ以外: `data-source` ステップへフォールバック
3. フォアグラウンドとして自動遷移（遷移URLに build フラグを付与）
4. 遷移先画面は、そのビルドセッションを購読する状態で表示され、進捗/停止を可能とする。

## 7. フォルダノードのビルドフロー
1. ビルドアクション発火時、配下対象を集約しビルドURL群を作成する。
2. キュー登録は行うが、初期遷移は行わない（バックグラウンド）。
3. 実行中にユーザーが該当ステップを手動遷移すると、同セッションを購読可能な状態で閲覧/停止操作が可能。
4. 画面遷移を伴わないため、完了・失敗通知はキュー/セッション状態購読を通じて反映する。

## 8. ステータス判定（styler など URL Download 連携のための補足）
1. styler の「ビルドが必要」判定は、`URL Download` など外部取得手段が「未完了」の場合にも真とする。
2. ただし、URL指定自体があり、ビルドセッション内でダウンロードが未実行かつ必要状態なら、待機中扱い（ビルド必要）とする。
3. すなわち、URL文字列だけ存在して成功済みでない場合は「ビルドが必要」状態を維持する。

## 9. 例外と制約
1. ノード種別ごとの特殊 UI/状態は個別プラグイン側で定義するが、ビルド起点・キュー規則・遷移規則は本仕様を優先する。
2. フォアグラウンド／バックグラウンドの切替はノード種類でなく「個別/フォルダ」の分類で決まる。
3. 例外的にビルドターゲット解決不能なノードでは、build 実行を開始できない（事前にビルドボタンを無効化）。

## 10. 受け入れ基準（DoD）
- 個別ノードのビルド実行で、対象ステップへ必ず自動遷移し、セッション進捗の購読に入ること。
- フォルダノードのビルド実行で、初期遷移なしにキュー登録され、実行開始時にバックグラウンドで進行すること。
- styler の場合、`build` ステップ不在時に `data-source` へフォールバックして遷移すること。
- ステータス更新時、URL Download で未実行のダウンロードは「ビルドが必要」と判定されること。
- セッション中の停止/中断操作が、同一セッション購読コンポーネント上で一貫して有効化されること。
