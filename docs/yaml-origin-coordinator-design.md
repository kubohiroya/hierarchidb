# YAML origin-wide coordinator design

## Purpose

The YAML storage activation requires a release-independent directory of browser execution
contexts before the production quiescence bridge can connect the dormant legacy fence protocol.
The coordinator described here is a participant directory and bootstrap gate. It is not the
storage activation state machine and it never establishes the IndexedDB write fence.

The coordination domain is one browser profile and storage partition within the exact
HierarchiDB Service Worker registration scope. Another browser profile, private browsing
partition, device, origin, or Service Worker scope has a distinct CoreDB and a distinct
coordinator.

## Current limitation

The production runtime uses a SharedWorker URL generated by Vite and appends the application
version as a query parameter. Different releases can therefore retain different SharedWorker
instances. A SharedWorker can enumerate its own connected ports, but it cannot enumerate an old
release's SharedWorker or a window that has not connected to it. BroadcastChannel and Web Locks
are cooperative transports and do not provide an authoritative client directory for code that
predates those transports.

## Fixed Service Worker registration

The coordinator is built as `hdb-origin-coordinator.js` at the application base path and is
registered with that same base path as its scope. The production registration is therefore:

```text
script: /hierarchidb/hdb-origin-coordinator.js
scope:  /hierarchidb/
protocol version: 1
```

The coordinator script has no `fetch` listener and implements no cache, offline fallback,
request rewriting, or PWA behavior. Its fixed URL is not a compatibility alias for application
code. It is the stable registration anchor used by the browser to maintain one active Service
Worker for the scope.

The coordinator calls `clients.claim()` during activation. Client census uses
`clients.matchAll({ includeUncontrolled: true, type: 'all' })`, followed by an exact origin and
scope-path check. Same-origin applications outside the registration scope are never included.

## Participant identity and census

The browser-issued `Client.id` is the participant identity. The application does not generate,
persist, infer, or default participant IDs. Window clients map to the dormant protocol's `tab`
kind. Dedicated and SharedWorker clients map to `worker` when the later quiescence bridge creates
the participant snapshot.

Foundation census probes every in-scope window, dedicated worker, and SharedWorker client. A
foundation-capable client returns an exact response over the transferred MessagePort. A client
that does not respond is not removed from the result. A later bridge may accept browser-proven
client destruction through a separately specified typed protocol event, but it must not convert
silence into destruction or acknowledgement.

Census results expose only counts by browser client type and a stable status code. Client IDs,
URLs, raw messages, runtime errors, credentials, endpoints, and storage content remain private to
the coordinator.

## Strict foundation messages

All message validators inspect exact own data properties. Accessors, symbol properties, missing
properties, extra properties, arrays, non-plain objects, unknown literal values, release IDs other
than the exact 40-character build source SHA, and unsupported protocol versions are rejected
without invoking getters. HELLO and every census response must equal the source SHA embedded in
the coordinator build; a different valid SHA is incompatible and never accepted as the current
release.

Window bootstrap sends:

```ts
{
  type: 'HDB_COORDINATOR_HELLO';
  protocolVersion: 1;
  releaseId: string;
  capabilities: readonly ['origin-coordinator-foundation-v1'];
}
```

The coordinator returns an accepted decision only after reading and validating the durable gate:

```ts
{
  type: 'HDB_COORDINATOR_HELLO_RESULT';
  protocolVersion: 1;
  status: 'accepted';
  legacyYamlAccess: 'allowed';
}
```

Foundation readiness requires an explicit non-empty request ID and an explicit positive safe
integer timeout. There is no default timeout or automatic retry. The response distinguishes
compatible, incompatible, unresponsive, and browser-proven discarded counts for each client
type. Any incompatible or unresponsive client makes readiness rejected.

## Durable bootstrap gate

The Service Worker is restartable and its module memory is not authoritative. It owns a dedicated
IndexedDB database:

```text
database: hierarchidb-origin-coordinator
store: coordinator-state
key: yaml-storage
version: 1
```

The first database upgrade creates exactly one frozen-shape record:

```ts
{
  key: 'yaml-storage';
  protocolVersion: 1;
  phase: 'allowed';
}
```

The foundation does not expose any operation that changes this record. A missing record in an
existing store, an unknown phase, a protocol mismatch, an accessor, an extra property, an IDB
failure, or an unavailable Service Worker is a visible bootstrap rejection. Those conditions are
never converted to `allowed`.

The generic application IndexedDB reset action excludes the coordinator database. Removing this
database is an explicit rollback operation only; ordinary schema recovery must not erase the
durable gate and rely on a later Service Worker install to recreate it.

The later quiescence bridge will extend the durable gate with monotonic `revoked` and `rejected`
states in its own Issue. It must not add TTL expiry, automatic reset, or an implicit return to
`allowed`.

## Bootstrap order

Every foundation release window performs these steps in order:

1. Resolve the exact application base path and exact build source SHA.
2. Register or obtain the fixed Service Worker registration.
3. Wait for its active worker with the caller-supplied deadline.
4. Send the strict HELLO request and require an accepted durable gate decision.
5. Install the readiness responder.
6. Only then initialize browser globals, preload plugin worker stores, create the router, or start
   the SharedWorker runtime.

The strict census contract, build-SHA reader, and responder live in the shared
`@hierarchidb/origin-coordinator` workspace package. The window, SharedWorker, dedicated runtime
worker, stage worker, GEOS worker, country availability worker, and tabular filter worker all use
that one contract. Every worker entry installs the responder before its runtime bootstrap or
application message handler begins. The foundation responder does not revoke entrypoints, close
storage, or acknowledge quiescence.

## Authority boundary

Foundation readiness and later cooperative quiescence always retain
`actualFenceEstablished: false`. Only the target CoreDB IndexedDB `versionchange` phase is the
actual storage fence. CoreDB schema registration, migration preflight, target `open()`, migration,
canonical publication, YamlDB access, and the dormant activation state machine remain unreachable
from this foundation.

## Failure and rollback

- Unsupported Service Worker APIs, an inactive registration, timeout, malformed data, invalid
  durable state, and census incompatibility are visible typed failures.
- Native registration failures are converted to a stable error code; browser exception text and
  registration URLs are not returned as public coordinator errors.
- The foundation does not retry registration, replace the fixed scope, fall back to a
  BroadcastChannel or Web Lock, or continue legacy bootstrap after rejection.
- Before the production responder exists, rollback is allowed only when the durable gate is the
  valid `allowed` record. The app registration, fixed artifact, bootstrap integration, Service
  Worker registration, and coordinator database are then removed by an explicit rollback action.
- Once a later responder or activation release is connected, the coordinator must not be removed
  before the connector, activation, and any required inverse migration are rolled back in order.
