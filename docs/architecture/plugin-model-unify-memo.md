# メモ: 「シンプル/拡張」プラグイン分類を統一する理由と方針

作成日: 2025-09-05
対象: packages/plugins/README.md, スキャフォールド/テンプレート, テスト命名

## 結論
- 実装上は単一の `PluginDefinition` で十分（`extends?: NodeType`, `dependencies: NodeType[]`）。
- 「シンプル/拡張」という二分類は概念上の便宜に留まっており、学習コストと文書の重複を生む。
- 用語・図・テンプレートを「プラグイン（extends あり/なし）」に統一する。

## なぜ集約できるのか（技術的根拠）
- ランタイム登録フローは単一: 依存解決（トポロジカル順）→ 定義の読み込み → ハンドラ登録 → UI エントリ解決。
- 「拡張」も `extends` と `dependencies` の情報だけで表現可能。特別な API や別型を要求しない。
- UI/Worker いずれも `~/plugin-registry` に集約済みで、分岐は不要。

## なぜ集約すべきか（プロダクト/運用上の利点）
- 認知負荷の削減: 新規参加者が覚える分類が1つになる。
- ドキュメントの重複解消: 同一の実装モデルを2通りに説明する必要がなくなる。
- テンプレート/スキャフォールドの単純化: 1フローに統一（`extends` の有無はオプション）。
- URL/nodeType の一貫性: 短い `nodeType` 命名と整合し、外部に露出する表現が単純になる。

## 影響と移行
- ドキュメント: README の図（SIMPLE/EXTENDING/MIXIN）を簡素化し、「extends あり/なし」の説明に置換。
- テンプレート: 分岐があれば1つに統合し、`extends` はテンプレート引数へ。
- テスト/コメント: 旧用語（simple/extended）を検索置換し、名称を統一。
- ランタイム: 既存コードに機能差はないため、実装変更は不要（用語と図の更新が主）。

## リスクと対応
- 既存ドキュメントとの齟齬: 差分をリリースノートに明記し、参照先を新章に誘導。
- 外部記事/資料との用語不一致: README 冒頭に用語統一の注記を追加。

## 受け入れ基準（DoD）
- README から「シンプル/拡張」の語が消え、「extends あり/なし」の説明に置換されている。
- Mermaid 図が簡素化され、依存/継承の一本化が表現されている。
- スキャフォールド/テンプレート/テスト名の旧語が整理されている。
- ルートで `pnpm typecheck` がグリーン。

## ロールバック
- ドキュメント差分をリバートするだけで元に戻せる（コード改変は想定しない）。
