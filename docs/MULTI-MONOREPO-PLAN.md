# マルチモノレポ運用構想（ドラフト）

**ステータス: 初回リリース後に再検討予定**

## 目的
- ビルド時間・開発体験の改善
- 安定領域と活発開発領域を物理的に切り分け、依存管理を明確化
- 監視（watch）対象を必要最小限に絞り、ローカル開発の負担を軽減

## 想定構成案
| レポジトリ | 代表パッケージ例 | 監視ポリシー | 備考 |
|-------------|------------------|--------------|------|
| `hierarchidb-core` | `@hierarchidb/common-*`, `@hierarchidb/runtime-worker`, UI 基盤 (`@hierarchidb/ui-*`) など | 基本監視なし。必要時にパッケージ単位または全体を手動ビルド。 | 安定領域。ビルド成果物を別レポジトリへ供給。 |
| `hierarchidb-app` | `@hierarchidb/app`（エンドユーザー向け SPA） | Vite/React Router dev サーバで通常の HMR を有効化。 | core / plugins を依存として取り込み。 |
| `hierarchidb-plugins` | `@hierarchidb/plugins-{shape,location,route,...}` など | 環境変数 `WATCH_PACKAGES` でカンマ区切り指定し、該当パッケージごとに `tsup --watch` を起動。 | アクティブ開発領域。必要なプラグインのみ watch。 |

## 運用イメージ
1. **core**
   - 原則として安定実装のみ。ウォッチ対象外。
   - 変更時は `pnpm --filter <pkg> build` や CI でのまとめビルドを実行。
   - 成果物（`dist/` および型定義）を npm レジストリ／アーティファクトで提供。

2. **app**
   - `pnpm dev` が Vite もしくは React Router dev server を起動。
   - HMR により UI 作業の反映を重視。
   - core / plugins の更新を取り込む際は、依存解決やバージョン更新を行う。

3. **plugins**
   - `pnpm dev`（仮）で環境変数を読み取り、対象パッケージごとに `tsup --watch` をスポーン。
   - 監視対象を柔軟に絞り込みつつ、ホットビルドで UI/Worker 両面の検証を行う。

## 想定メリット
- 安定領域の再ビルドを避け、日常開発での待ち時間を削減。
- 監視対象を限定でき、`tsup --watch` プロセス数を制御可能。
- 各レポジトリの責務が明確になり、リリースフローの整理が容易。

## 想定課題 / 未決事項
- **依存解決**: core → app / plugins の依存をどう流通させるか（npm 発行、内部レジストリ、pnpm link 等）。
- **CI/CD**: 3 レポジトリでのビルド・テストパイプライン設計、成果物共有の方式。
- **同時変更の扱い**: core と plugins の同時更新が必要な場合のワークフロー定義。
- **リリース管理**: バージョン整合性（SemVer / workspace protocol）とロールバック手順の策定。
- **ドキュメント整備**: 開発者向けセットアップ手順、watch スクリプトの利用方法など。
- **監視フローの自動化**: mrtask × tsup 自動起動と、Nx の watch 機能をどう位置づけるか。

### 監視・ビルドのワークフロー案

| 案 | 概要 | メリット | 留意点 |
|-----|------|---------|--------|
| **mrtask 連携（案）** | mrtask タスク定義の `dir1`,`dir2` メタデータを利用し、worktree 作成時に対象パッケージの `tsup --watch` を自動 spawn。再開用コマンド（例: `pnpm watch:resume`）で停止したプロセスを復帰。 | タスク単位で監視対象が明示され、パッケージ境界を意識した作業にフィット。既存運用（mrtask）と親和性が高い。 | watch スクリプト・プロセス管理（ログ整形/終了処理）の実装と保守が必要。複数 watch を扱うため、リソース使用量には注意。 |
| **Nx workspace watch** | Nx の `run-many --watch` や `nx watch` を活用し、Nx プロジェクトとしてターゲット（build 等）を監視実行。依存グラフに基づく差分ビルドやキャッシュが利用可能。 | 仕組みが標準化され、依存関係解析や再実行の最適化が得られる。Nx の機能群と統合しやすい。 | 現行の tsup 設定やコマンドを Nx ターゲットへ移植する必要がある。mrtask ワークフローとの統合には追加設計が必要。 |

現状は mrtask ベースのワークフローを維持しながら、追加スクリプトで監視を補完する方向が自然と見込まれる。将来的に Nx を導入する場合は、プロジェクト設定やターゲット定義の再設計を伴うため、分割後の体制と合わせて再検討する。

## 当面の方針
- 初回リリース完了までは現行モノレポを維持し、必要最小限の監視改善で対応。
- リリース後に再度メリット／コストを精査し、必要なら段階的に分割作業へ着手。
- 分割を実施する場合は、依存棚卸しと CI 流れの設計から着手する。
