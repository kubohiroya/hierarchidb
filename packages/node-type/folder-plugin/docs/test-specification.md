# Folder Plugin テスト仕様書

## 概要
本ドキュメントは、folder-pluginのユーザシナリオに基づいたテスト仕様を定義します。フォルダノードの作成・編集における段階的な情報構築と、バッチ処理の進捗管理を包括的にテストします。

## ユーザシナリオ

### シナリオ1: フォルダノードの段階的作成
**目的**: ユーザが新しいフォルダノードを作成し、段階的に情報を構築していくプロセス

1. **開始**: ユーザがフォルダノード作成を開始
2. **基本情報入力**: フォルダ名、説明を入力
3. **メタデータ設定**: タグ、カスタムプロパティを追加
4. **中断・再開**: 作業を中断し、後で再開
5. **完了**: 全ての情報を確認し、ノード作成を完了

### シナリオ2: 既存フォルダノードの編集
**目的**: 既存のフォルダノードを編集し、変更を段階的に適用

1. **編集開始**: 既存フォルダノードの編集モードに入る
2. **情報変更**: 名前、説明、メタデータを変更
3. **プレビュー**: 変更内容をプレビュー
4. **破棄・やり直し**: 変更を破棄して再編集
5. **保存**: 変更を確定して保存

### シナリオ3: フォルダノードのバッチ処理
**目的**: 複数のフォルダノードに対する一括操作

1. **バッチ開始**: 複数フォルダノードを選択してバッチ処理開始
2. **進捗確認**: 処理の進捗状況を確認
3. **プレビュー**: バッチ処理結果のプレビュー
4. **中断・再開**: 処理を中断し、後で再開
5. **完了・破棄**: 処理を完了または破棄

## テストケース

### TC1: フォルダノード作成フロー

#### TC1.1: 基本的な作成フロー
- **前提条件**: データベース初期化済み
- **手順**:
  1. WorkingCopyを作成
  2. フォルダ基本情報を設定
  3. メタデータを追加
  4. WorkingCopyをコミット
- **期待結果**: 
  - CoreDBにフォルダノードが保存される
  - 全ての属性が正しく設定される

#### TC1.2: 作成中の中断と再開
- **前提条件**: WorkingCopy作成済み
- **手順**:
  1. WorkingCopyに部分的な情報を設定
  2. セッションを中断（WorkingCopyは保持）
  3. WorkingCopyを再読み込み
  4. 残りの情報を設定
  5. コミット
- **期待結果**:
  - 中断前の情報が保持される
  - 再開後に追加した情報と合わせて保存される

#### TC1.3: 作成の破棄
- **前提条件**: WorkingCopy作成済み、情報設定済み
- **手順**:
  1. WorkingCopyに情報を設定
  2. WorkingCopyを破棄
- **期待結果**:
  - EphemeralDBからWorkingCopyが削除される
  - CoreDBに変更が反映されない

### TC2: フォルダノード編集フロー

#### TC2.1: 基本的な編集フロー
- **前提条件**: 既存フォルダノード存在
- **手順**:
  1. 既存ノードからWorkingCopyを作成
  2. 各属性を変更
  3. 変更をコミット
- **期待結果**:
  - CoreDBのフォルダノードが更新される
  - 変更履歴が記録される

#### TC2.2: 編集のプレビューと確認
- **前提条件**: WorkingCopyで変更済み
- **手順**:
  1. 変更内容をプレビュー
  2. 差分を確認
  3. 必要に応じて再編集
  4. 最終確認後コミット
- **期待結果**:
  - プレビューで変更内容が正確に表示される
  - 差分が正しく計算される

#### TC2.3: 編集の破棄とやり直し
- **前提条件**: WorkingCopyで変更済み
- **手順**:
  1. 変更を行う
  2. 変更を破棄
  3. 新しいWorkingCopyを作成
  4. 別の変更を行う
  5. コミット
- **期待結果**:
  - 最初の変更が反映されない
  - 2回目の変更のみが反映される

### TC3: バッチ処理フロー

#### TC3.1: 複数フォルダの一括更新
- **前提条件**: 複数のフォルダノード存在
- **手順**:
  1. バッチ処理を開始
  2. 複数ノードを選択
  3. 共通の変更を定義
  4. バッチを実行
- **期待結果**:
  - 全選択ノードが更新される
  - トランザクション的に処理される

#### TC3.2: バッチ処理の進捗管理
- **前提条件**: 大量のフォルダノード存在
- **手順**:
  1. バッチ処理開始
  2. 処理中に進捗を確認
  3. 進捗イベントを監視
- **期待結果**:
  - 進捗が正確に報告される
  - 処理済み/未処理の数が正しい

#### TC3.3: バッチ処理の中断と再開
- **前提条件**: バッチ処理実行中
- **手順**:
  1. バッチ処理を開始
  2. 途中で中断
  3. 中断位置を記録
  4. 処理を再開
  5. 完了まで実行
- **期待結果**:
  - 中断位置が正確に記録される
  - 再開時に重複処理されない
  - 全ノードが最終的に処理される

#### TC3.4: バッチ処理のプレビュー
- **前提条件**: バッチ処理定義済み
- **手順**:
  1. バッチ処理を定義
  2. プレビューモードで実行
  3. 結果を確認
  4. 実際の処理を実行
- **期待結果**:
  - プレビューでは実際の変更が行われない
  - プレビュー結果と実行結果が一致する

#### TC3.5: バッチ処理の破棄
- **前提条件**: バッチ処理実行中または完了前
- **手順**:
  1. バッチ処理を開始
  2. 処理を破棄
- **期待結果**:
  - 処理済みの変更がロールバックされる
  - 全ノードが元の状態に戻る

## テスト環境

### 必要なモック/スタブ
- fake-indexeddb: IndexedDBのメモリ実装
- Worker環境のモック
- Comlinkのモック実装

### テストデータ
- サンプルフォルダノード
- メタデータテンプレート
- バッチ処理用の大量データセット

## 成功条件
- 全テストケースが成功
- カバレッジ80%以上
- パフォーマンス基準を満たす（バッチ処理1000件/秒以上）

## リスクと対策
- **リスク**: WorkingCopyの状態管理の複雑さ
- **対策**: 状態遷移図に基づいた厳密なテスト
