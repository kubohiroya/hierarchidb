# Node-type Plugins 共通化ギャップ分析（2025-09-07）

対象: `shape-plugin` / `location-plugin` / `route-plugin`

凡例: 本書ではチェックリストにおける「△（共通化の余地あり）」の箇所について、現状の注記と今後の修正内容（案）を列挙する。DoD とロールバック方針も最小限で付す。

---

## 1) エンティティ定義/ハンドラ（BaseEntityHandler 準拠）

- 該当プラグイン: shape（△）
- 参照: `packages/node-type/shape-plugin/src/services/ShapeEntityHandler.ts` は `@hierarchidb/base-plugin` を未使用。`location`/`route` は `BaseEntityHandler` を採用。

注記（現状/課題）
- shape のエンティティ CRUD/WorkingCopy が独自実装で、検索条件やテーブル抽象（Dexie Table 型）などの基盤差異が生じている。
- 共通メタデータ検索（`BaseSearchCriteria`）やテーブルアクセスの型整合が取りにくい。

今後の修正
- shape のハンドラを `BaseEntityHandler<ShapeEntity, Create/Update 型, FilterCriteria>` へ段階移行。
- 独自 ID 発行/WorkingCopy 取り回しを `BaseEntityHandler` 側の拡張ポイントに委譲（Adapter 層を挿入）。
- 影響範囲: shape ワーカー API と DB ラッパの呼び出し部。

DoD
- shape の CRUD が `BaseEntityHandler` 継承に置換され、既存ユースケースが動作（単体テスト合格）。

ロールバック
- フラグ `SHAPE_BASE_HANDLER_V2` で切替。問題発生時は OFF にして従来実装へ回帰。

---

## 2) バッチセッション基盤（AbstractBatchSession / BatchService）

- 該当プラグイン: shape（△）, location（△）
- 参照:
  - route: `RouteBatchSession.ts` は `AbstractBatchSession` + `BatchService` を採用（レーン制御/カーソル更新を内包）。
  - location: `LocationBatchManager.ts` は独自の並列・進捗実装で `AbstractBatchSession` を未使用。
  - shape: `batch/ShapeBatchSession.ts` は旧パスで `AbstractBatchSession` を参照しつつ、並列処理は `BatchSessionManager.ts` 側に残存。

注記（現状/課題）
- shape は「マネージャ + セッション」の二重構成で責務が分散。location は完全独自で進捗/中断モデルが非互換。

今後の修正
- location を `AbstractBatchSession` ベースに移行（`LocationBatchSession` 新設）。
- shape は `BatchSessionManager` の実行責務を `ShapeBatchSession` へ集約し、旧 API はファサード化のみ残す。
- 共通ユーティリティ（カーソル更新、ポーリング一時停止、mapChunks 呼び出し）を `@hierarchidb/runtime-shared-batch-processor` 側に一本化。

DoD
- location/shape ともにバッチ進捗・一時停止・再開・取消 API のシグネチャ/意味が route と整合。

ロールバック
- `LOCATION_BATCH_V2` / `SHAPE_BATCH_V2` フラグで段階導入。OFF で旧フローに戻す。

---

## 3) ステージ構成の共通化（download → simplify → vectortile 等）

- 該当プラグイン: location（△）, route（△）
- 参照: shape は 4 段（download/simplify1/simplify2/vectortile）。location は `search→geocoding→validating→saving`。route は shape のステージ名を一部流用（`simplify1/2` を検証段に再割当）。

注記（現状/課題）
- ステージ名と意味がプラグイン毎にズレ、横断的な進捗 UI/ログ集計の可読性が低い。

今後の修正
- 共通ステージ語彙を定義：`ingest`（外部取得）, `process1`, `process2`, `optimize`, `persist`。
- shape: download→ingest, simplify1→process1, simplify2→process2, vectortile→optimize にマッピング。
- location: search/geocoding→ingest, validating→process1, saving→persist に整理。
- route: location_resolution→ingest, route_generation→process1, validation→process2, optimization→optimize。

DoD
- 各セッションの進捗イベントに共通ステージ名が出力される（UI 側の凡例 1 箇所で説明可能）。

ロールバック
- 旧→新のステージ名マッピングテーブルを保持し、UI 側で双方向変換を許可。

---

## 4) データソース/戦略レジストリ化

- 該当プラグイン: route（△）
- 参照: location は `services/download/registry` に戦略（例: `NominatimStrategy`）登録。route は `RouteGenerator` へ `engines` DI（OSRM/searoute 等）だがレジストリ不在。

注記（現状/課題）
- route のエンジン切替は DI 前提で、UI/設定からの選択やカナリア配布が難しい。

今後の修正
- `@hierarchidb/route-engine-registry`（軽量）を新設し、`id`, `capabilities`, `factory` を登録/列挙可能に。
- `RouteGenerator` はレジストリから `method`/`options` に応じてエンジン解決。fallback は direct。

DoD
- `osm_route`/`searoute`/`direct` をレジストリ経由で切替。環境変数/Feature Flag で優先度上書き可能。

ロールバック
- レジストリ層を OFF にして従来の直接 DI を継続可能。

---

## 5) 進捗イベントモデル（ProgressEvent 等）

- 該当プラグイン: location（△）
- 参照: route は `ProgressEvent` を使用。shape は 25/50/75/100 のステージ進捗を発火。location は `LocationBatchProgressEvent` 独自。

注記（現状/課題）
- location の独自型により UI/集計の型分岐が増大。

今後の修正
- `ProgressEvent` に `domain: 'shape'|'location'|'route'` と `stage` を標準化。location 側の発火点を置換。
- 旧イベントは互換アダプタで受理（移行期間）。

DoD
- 3 プラグインの進捗イベントが共通型に準拠し、UI の型分岐が削減。

ロールバック
- `LOCATION_PROGRESS_V2` フラグで戻せるよう旧イベント発火を温存。

---

## 6) リトライ/レジューム/リカバリ戦略

- 該当プラグイン: location（△）, route（△）
- 参照: shape は `services/RecoveryStrategy.ts`（指数バックオフ/並列度削減/チェックポイント/フォールバック等）。location は簡易、route は簡易リトライのみ。

注記（現状/課題）
- 高負荷/401 復帰/外部 API 変調時の回復性に差。仕様も横断で説明しづらい。

今後の修正
- `@hierarchidb/recovery` を抽出（Strategy/Context/Result を共通化）。
- location/route へ同 API を適用し、`resumePoint` と `reduction strategies`（並列/データ量）を活用。

DoD
- 意図的に 429/503 を発生させる統合テストで 3 プラグインが回復（最大リトライ/フォールバック動作を記録）。

ロールバック
- プラグイン側の Strategy 注入を環境変数で無効化して従来動作に退避。

---

## 7) 並列度制御（セマフォ/レーン別上限）

- 該当プラグイン: shape（△）, location（△）
- 参照: route はメソッド別レーン（`osm_route:1`,`searoute:3` 等）。shape/location は一律並列制御中心。

注記（現状/課題）
- 外部 API のスロットル/帯域をまたぐ最適化が不足し、スパイクで失敗率が上がりうる。

今後の修正
- shape/location に「データソース/戦略/エンジン」単位のレーンセマフォを導入。既存の `BatchService` 並列と多重にならないよう制御点を一本化。

DoD
- 各プラグインにレーン別の同時実行上限が設定可能になり、負荷試験でエラー率が低下。

ロールバック
- `*_LANE_LIMITS=0` でレーン制御を無効化。

---

## 8) 認証連携/401 ハンドリングの共通化

- 該当プラグイン: location（△）
- 参照: shape は `AuthNotificationRegistry` で UI 復帰と再試行を連動。location は `authFetch` の呼び出しが点在しレジストリ未使用。

注記（現状/課題）
- 401/403/トークン失効時の UX が不統一。リトライ/中断のシグナル経路も別実装。

今後の修正
- location にレジストリ購読を実装し、認証要求/成功/中止イベントでバッチの pause/resume/cancel を制御。
- 低リスク導入のため、まず Nominatim/Overpass 経路のみで有効化。

DoD
- e2e（mock 401）で location バッチが自動一時停止→サインイン→自動再開する。

ロールバック
- `LOCATION_AUTH_REGISTRY=0` で旧動線へ。

---

## 9) ベクタータイル最適化ステージ

- 該当プラグイン: route（△）
- 参照: shape は `VectorTileWorker.ts` で MVT 相当の出力を持つ。route は `optimization` タスクがダミー。

注記（現状/課題）
- 大量ルート描画の LOD/タイル化が未整備。

今後の修正
- shape のタイル化ロジックを `@hierarchidb/vector-tiler-lite` として切り出し、route の最終段で再利用。ライン向けに簡易クリップ/属性縮約を追加。

DoD
- 大域/中域/近接ズームで FPS がベースライン比改善し、ルート数 1e4 規模で描画/パンが実用性を満たす。

ロールバック
- フラグ `ROUTE_TILER_V2` で OFF に戻す。

---

## 10) UI フロー（ウィザード/ダイアログ）の共通部品

- 該当プラグイン: shape（△）, route（△）
- 参照: location は `LocationDialog/Panel/steps/*` など UI 部品が整備。shape/route は独自/薄い。

注記（現状/課題）
- 入力検証/ライセンス確認/プレビュー/進捗表示の UI パターンが分散し再利用性が低い。

今後の修正
- `@hierarchidb/ui-batch-wizard` を新設（Step/Progress/Resume/TabularPreview の共通コンポーネント）。
- shape/route のダイアログを置換。location は先行実装をベースに抽象化。

DoD
- 3 プラグインで進捗/再開/タブular 表の UI が同一コンポーネント実装になる。

ロールバック
- パッケージレベルの feature flag で旧ダイアログへ切替可能。

---

## 11) 検証/フィルタリング・パイプライン

- 該当プラグイン: location（△）, route（△）
- 参照: location は `validateAndFilterLocations` が内蔵。route は `validation` タスクがスケルトン。shape は面積/ズーム統計等の下地あり。

注記（現状/課題）
- ルール定義/チェーン構築の API が不統一で、共通ルール（重複/範囲/属性必須）を横展開しづらい。

今後の修正
- `@hierarchidb/validation-pipeline` を導入（Sync/Async Rule, combinator, metrics 付き）。
- location/route に標準ルール（重複除去、距離/面積閾値、必須属性、座標正常性）を適用。shape は既存ロジックをルール化。

DoD
- 3 プラグインで同一のエラーレポート構造（件数、原因分類、サンプル）が得られる。

ロールバック
- 旧バリデーション呼び出しを残し、フラグで切替。

---

## 12) ストレージ抽象（Dexie/DB ラッパ）

- 該当プラグイン: location（△）
- 参照: shape は `ShapeDB.ts`、route は `RouteDatabase.ts` を保有。location は永続/カーソル層が未統一。

注記（現状/課題）
- 中断再開/タブular 書き出し/インデックス最適化がプラグイン間で異なる。

今後の修正
- `LocationDatabase` を新設（entities, cursors, results, tables）。TabularWriter 連携を標準化。

DoD
- location のバッチセッションがカーソル更新/再開/Tabular 出力に対応し、route/shape と API が一致。

ロールバック
- 旧メモリ型/直接保存実装をフラグで選択可能。

---

## 13) 一時停止/再開/取消 API

- 該当プラグイン: route（△）
- 参照: route はカーソル `paused` ポーリングで実質 Pause を実装するが外部 API として未露出。shape は `BatchSessionManager` に明示 API がある。location は未整備。

注記（現状/課題）
- 操作 UI の統一が難しく、e2e からの制御も異なる。

今後の修正
- `AbstractBatchSession` に `pause/resume/cancel` のコマンドハンドラを標準化し、route のファサード層から公開。
- location も v2 セッション移行時に同 API を実装。

DoD
- 3 プラグインとも同一関数シグネチャ/イベントで一時停止系が動作。

ロールバック
- ファサードで旧挙動にフォールバック可能。

---

## 付録: 実施順序と依存関係（提案）

1. ProgressEvent 標準化（共通ステージ語彙・UI 影響少）
2. route のエンジン・レジストリ導入（DI 互換で低リスク）
3. location の BatchSession v2 化（影響中）
4. shape の Batch 集約/旧 Manager ファサード化（影響中）
5. 検証パイプライン共通化（ルール追加は段階）
6. レーン別並列制御の導入（段階展開）
7. 認証レジストリの location 連携（OSM 系に限定して開始）
8. ルート用ベクタータイル最適化（ベータ→既定 OFF）
9. UI 共通ウィザード抽出（追随リファクタ）

各ステップは既定 OFF のフィーチャーフラグで段階導入し、`TASKS.md` の DoD/ロールバックと運用ログに反映すること。
