# Location Plugin テスト仕様書

## 概要
本ドキュメントは、location-pluginのユーザシナリオに基づいたテスト仕様を定義します。地理的位置情報を持つノードの作成・編集における段階的な情報構築と、バッチ処理による地理データの一括操作を包括的にテストします。

## ユーザシナリオ

### シナリオ1: ロケーションノードの段階的作成
**目的**: ユーザが新しいロケーションノードを作成し、段階的に地理情報を構築していくプロセス

1. **開始**: ロケーションノード作成を開始
2. **基本情報入力**: 場所名、説明を入力
3. **座標設定**: 緯度・経度を設定（手動入力または地図選択）
4. **詳細情報追加**: 住所、タイムゾーン、メタデータを追加
5. **中断・再開**: 作業を中断し、後で再開
6. **完了**: 全ての情報を確認し、ノード作成を完了

### シナリオ2: 既存ロケーションノードの編集
**目的**: 既存のロケーションノードを編集し、位置情報や関連データを更新

1. **編集開始**: 既存ロケーションノードの編集モードに入る
2. **位置変更**: 座標を新しい場所に更新
3. **境界設定**: エリアの境界（ポリゴン）を定義
4. **プレビュー**: 地図上で変更内容をプレビュー
5. **破棄・やり直し**: 変更を破棄して再編集
6. **保存**: 変更を確定して保存

### シナリオ3: ロケーションノードのバッチ処理
**目的**: 複数のロケーションノードに対する一括操作

1. **バッチ開始**: 複数ロケーションノードを選択してバッチ処理開始
2. **ジオコーディング**: 住所から座標を一括取得
3. **逆ジオコーディング**: 座標から住所を一括取得
4. **進捗確認**: 処理の進捗状況を確認
5. **中断・再開**: 処理を中断し、後で再開
6. **完了・破棄**: 処理を完了または破棄

## テストケース

### TC1: ロケーションノード作成フロー

#### TC1.1: 基本的な作成フロー
- **前提条件**: データベース初期化済み
- **手順**:
  1. WorkingCopyを作成
  2. 場所名と説明を設定
  3. 座標（緯度: 35.6762, 経度: 139.6503）を設定
  4. 住所情報を追加
  5. WorkingCopyをコミット
- **期待結果**: 
  - CoreDBにロケーションノードが保存される
  - 座標が正しく設定される
  - 住所情報が関連付けられる

#### TC1.2: 地図選択による座標設定
- **前提条件**: WorkingCopy作成済み
- **手順**:
  1. 地図インターフェースを開く
  2. 地図上で位置をクリック
  3. 座標が自動入力される
  4. 近隣のPOI（Point of Interest）を取得
  5. コミット
- **期待結果**:
  - クリック位置の座標が正確に取得される
  - 近隣POI情報が付加される

#### TC1.3: エリア（ポリゴン）の定義
- **前提条件**: WorkingCopy作成済み
- **手順**:
  1. 基本位置情報を設定
  2. 境界モードに切り替え
  3. ポリゴンの頂点を順次追加
  4. エリアを閉じる
  5. エリア情報（面積、周囲長）を計算
  6. コミット
- **期待結果**:
  - ポリゴンが正しく定義される
  - エリア情報が自動計算される

#### TC1.4: 作成中の中断と再開
- **前提条件**: WorkingCopy作成済み
- **手順**:
  1. 場所名と座標を設定
  2. セッションを中断
  3. WorkingCopyを再読み込み
  4. 住所とメタデータを追加
  5. コミット
- **期待結果**:
  - 中断前の情報が保持される
  - 再開後の追加情報が正しく保存される

#### TC1.5: 作成の破棄
- **前提条件**: WorkingCopy作成済み、情報設定済み
- **手順**:
  1. 完全な位置情報を設定
  2. WorkingCopyを破棄
- **期待結果**:
  - EphemeralDBからWorkingCopyが削除される
  - CoreDBに変更が反映されない

### TC2: ロケーションノード編集フロー

#### TC2.1: 座標の更新
- **前提条件**: 既存ロケーションノード存在
- **手順**:
  1. 編集用WorkingCopyを作成
  2. 新しい座標を設定
  3. 移動距離を計算
  4. コミット
- **期待結果**:
  - 座標が更新される
  - 移動距離が正しく計算される

#### TC2.2: 住所情報の更新
- **前提条件**: 既存ロケーションノード存在
- **手順**:
  1. 編集用WorkingCopyを作成
  2. 住所を変更
  3. ジオコーディングで座標を検証
  4. プレビューで確認
  5. コミット
- **期待結果**:
  - 住所が更新される
  - 座標との整合性が保たれる

#### TC2.3: タイムゾーンと地域情報の設定
- **前提条件**: 既存ロケーションノード存在
- **手順**:
  1. 編集用WorkingCopyを作成
  2. タイムゾーンを設定
  3. 国・地域コードを設定
  4. 言語設定を追加
  5. コミット
- **期待結果**:
  - タイムゾーンが正しく設定される
  - 地域情報が関連付けられる

### TC3: バッチ処理フロー

#### TC3.1: 住所からの一括ジオコーディング
- **前提条件**: 住所のみ設定された複数ノード存在
- **手順**:
  1. バッチ処理を開始
  2. ジオコーディング対象を選択
  3. ジオコーディングAPIを実行
  4. 結果を確認
  5. バッチを完了
- **期待結果**:
  - 全ノードに座標が設定される
  - エラーハンドリングが適切

#### TC3.2: 座標からの一括逆ジオコーディング
- **前提条件**: 座標のみ設定された複数ノード存在
- **手順**:
  1. バッチ処理を開始
  2. 逆ジオコーディング対象を選択
  3. 逆ジオコーディングAPIを実行
  4. 住所情報を取得
  5. バッチを完了
- **期待結果**:
  - 全ノードに住所が設定される
  - 地域情報が付加される

#### TC3.3: 距離計算バッチ処理
- **前提条件**: 複数のロケーションノード存在
- **手順**:
  1. バッチ処理を開始
  2. 基準点を設定
  3. 各ノードまでの距離を計算
  4. 距離でソート
  5. メタデータに距離を保存
- **期待結果**:
  - 全ノードの距離が計算される
  - 正確な測地線距離が使用される

#### TC3.4: エリア内判定バッチ処理
- **前提条件**: ポリゴンエリアと複数のポイントノード存在
- **手順**:
  1. バッチ処理を開始
  2. 判定エリアを選択
  3. ポイント・イン・ポリゴン判定を実行
  4. エリア内/外でタグ付け
  5. バッチを完了
- **期待結果**:
  - 正確な内外判定が行われる
  - 適切にタグが付与される

#### TC3.5: バッチ処理の進捗管理
- **前提条件**: 大量のロケーションノード存在（100個以上）
- **手順**:
  1. バッチ処理を開始
  2. API呼び出しを含む処理を実行
  3. 進捗状況を監視
  4. レート制限を考慮
  5. 完了を待つ
- **期待結果**:
  - 進捗が正確に報告される
  - API制限が遵守される
  - エラーリトライが機能する

#### TC3.6: バッチ処理の中断・再開・破棄
- **前提条件**: バッチ処理実行中
- **手順**:
  1. ジオコーディングバッチを開始
  2. 途中で中断
  3. 処理済みノードを確認
  4. 処理を再開
  5. 一部完了後に破棄
- **期待結果**:
  - 中断位置が記録される
  - 再開時に処理済みノードがスキップされる
  - 破棄時に全変更がロールバックされる

## 地理計算テスト

### 距離計算
- Haversine式による測地線距離
- Vincenty式による高精度距離
- 平面近似による高速計算

### エリア計算
- ポリゴン面積（Shoelace式）
- 周囲長
- 重心計算

### 座標系変換
- WGS84 ⇔ Web Mercator
- 度分秒 ⇔ 十進法
- UTM座標系への変換

## テスト環境

### 必要なモック/スタブ
- fake-indexeddb: IndexedDBのメモリ実装
- ジオコーディングAPIのモック
- 地図表示ライブラリのモック
- Worker環境のモック

### テストデータ
- サンプル座標セット（世界主要都市）
- 住所サンプル（各国形式）
- ポリゴンデータ（行政区域）
- タイムゾーンデータ

## パフォーマンス基準
- 単一ノード作成: 100ms以下
- ジオコーディング: 500ms/件以下
- 距離計算: 10ms/ペア以下
- バッチ処理: 100件/秒以上（API呼び出しを除く）

## 成功条件
- 全テストケースが成功
- カバレッジ80%以上
- パフォーマンス基準を満たす
- 地理計算の精度が仕様内

## リスクと対策
- **リスク**: 外部APIの依存性
- **対策**: モックAPIとフォールバック実装

- **リスク**: 地理計算の精度要求
- **対策**: 複数アルゴリズムの実装と検証
