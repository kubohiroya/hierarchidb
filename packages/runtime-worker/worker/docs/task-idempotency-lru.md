# タスク: Idempotency LRU（commandId の再投函デデュプリケーション）

目的
- 同一 `commandId` の再投函を副作用なく弾き、同一結果を即時返却する。
- ネットワーク/呼び出しリトライや二重送信に対する安全性を高める。

範囲
- `CommandProcessor` にサイズ上限付きの LRU キャッシュ（`commandId -> CommandResult`）を導入。
- `processCommand` 入口でヒット時は保存済み `CommandResult` を返却し、実行・スタック操作を行わない。
- 保存は「成功/失敗ともに」対象。上限超過時は最古を削除。

設計詳細
- 容量: `PERFORMANCE_CONFIG` に `MAX_IDEMPOTENCY_CACHE_SIZE` を追加（例: 500）。
- 保存キー: `commandId`（文字列完全一致）。
- 保存値: サニタイズ済み `CommandResult`（イベント履歴と整合）。
- TTL: 初期は未導入（容量制限のみ）。必要に応じて時間ベースの期限を将来追加。

実施手順
1) `CommandProcessor` に軽量 LRU 実装を追加（Map+リスト or 既存ユーティリティ）。
2) `processCommand` 冒頭でキャッシュ確認→ヒット時に即返却。
3) コマンド実行後（成功/失敗問わず）にキャッシュへ保存。
4) イベント/ログにも「idempotent-hit」を記録（サニタイズされた最小メタのみ）。

受け入れ基準
- 同一 `commandId` を連投しても DB/Undo スタックが二重更新されない。
- ヒット時に前回と同一 `CommandResult` が返る。
- 上限を超えると古いエントリが排出され、メモリ使用が制御される。

依存関係
- なし（Zod/レジストリ/Comlink型強化と並行可）。T5（イベント衛生化）と整合が望ましい。

テスト方針
- ユニット: 同一 `commandId` の2回目以降が即返却か、スタックサイズが増えないかを検証。
- 統合: リトライシナリオ（ネットワーク再送を模した重複呼び出し）で副作用が一度のみかを確認。

備考
- 返却するのは「当時の結果」であり、環境状態が変化していても再実行しない（idempotency の意図）。必要であれば「強制再実行」オプションを将来検討。
