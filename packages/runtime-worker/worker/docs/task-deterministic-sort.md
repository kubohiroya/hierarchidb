# タスク: 子ノードの決定的ソートの明示化（データモデル変更なし）

## 背景 / 目的
- 現行は `createdAt` での並びに依存しており、同値時の順序が不定になり得る。
- UI のチラつきやテストの非決定性を防ぐため、クエリ段階で決定的順序を保証する。

## スコープ（範囲）
- 含む: `CoreDB.listChildren`/`TreeQueryService` の返却順を「createdAt → name → id」の全順序へ統一。
- 含まない: ユーザー定義の並べ替え（index/position）導入、DB スキーマ変更。

## 成果物
- `src/services/CoreDB.ts` / `src/services/TreeQueryService.ts` のソート実装更新。
- 単体テスト: 同一 `createdAt` の混在時でも順序が決定的であることを検証。
- ドキュメント: 仕様追記（表示順は安定ソート、モデルは順序を保持しない）。

## 仕様詳細
- 並び順: `createdAt` 昇順、同値は `name` 昇順、さらに同値は `id` 昇順。
- filter: `removedAt` の除外は現行どおり。

## 実施手順
1. `CoreDB.listChildren` の `sortBy('createdAt')` を置換し、複合キーによる安定ソートを実装（メモリ上で可）。
2. `TreeQueryService` 側でのフォールバック取得も同様の順序規則を適用。
3. テスト追加（既存 DB/Query テストにケースを追加）。

## 受け入れ基準
- 同一データに対して常に同じ順序で返る。
- 既存の API 契約・機能に変更なし（データ内容・件数）。

## テスト計画
- ユニット: 生成日時が同一の兄弟ノード集合において、`name/id` に基づき決定的順序となる。
- 統合: UI 側のリスト表示で順序が安定し、再取得で変化しない。

## 依存関係
- なし（Zod 導入、他タスクと並行可）。

## リスクと緩和策
- リスク: 大量兄弟でのメモリソートに微小コスト。
  - 緩和: 兄弟数は限定的との前提。必要に応じて Dexie 複合インデックス採用を検討（将来）。

## ロールアウト
- マイナー変更として一括適用。リグレッションがあればロールバック可能。

## ロールバック
- 当該ソート実装を `createdAt` 単独に戻す。
